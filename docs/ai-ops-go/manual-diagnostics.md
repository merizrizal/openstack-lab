## 2. G1 candidate: distinct domains and authenticated local ingress

### 2.1 Security domains

The candidate uses separate OS-enforced, non-root process identities even if both processes execute the same Go runtime binary:

| Domain | Responsibility and allowed access | Must not receive |
| --- | --- | --- |
| Requesting CLI | Accept a deliberate operator action and send a named diagnostic request. It supplies only the requested target and bounded user-level arguments. | Reader credentials, SDK clients, authority to choose project/profile/endpoint/implementation, or authority to write protected state. |
| Credential-owning enforcement process | Authenticate the local caller, load protected trusted policy/configuration, own reader clients and the protected store, authorize each operation, and perform the bounded reads. | Root privileges, a mutation capability, or an automatic stronger-profile fallback. |
| OS/operator control plane | Provision and protect the two non-root identities, IPC access, trusted configuration, credential source, and data area; review/revoke configuration. | Application-agent authority to create accounts, alter permissions, provision infrastructure, or change host security policy. |

A common executable, package boundary, command-line flag, environment variable, or shared process is not the isolation boundary. The requester must not be able to read or replace the credential owner’s secrets, trusted policy, or protected records. The credential owner must refuse access to arbitrary local callers.

### 2.2 Candidate IPC and authorization flow

A candidate local transport is a permission-restricted Unix-domain socket authenticated by kernel-supplied peer credentials (for example, Linux peer-credential facilities). The operator—not the application—would provision the socket directory and OS identities. The credential owner would validate the connecting peer against an independently protected allowlist and derive the authorization context from that peer plus current trusted configuration. No principal, project, capability, endpoint, credential, policy version, or limit in the request body is authoritative; request fields may only narrow the server-derived grant.

The socket path and identities are intentionally not selected here. Socket ownership/mode, ancestor-directory protection, no-follow/replacement behavior, peer-credential checks, connection lifecycle, and revocation behavior require implementation review and target-OS tests. Peer credentials identify an OS principal, not a particular executable: this candidate is acceptable only if the requesting principal is sufficiently isolated that untrusted processes cannot run as it or inherit its authority. If that cannot be demonstrated, do not enable this transport; obtain review of a stronger independently enforced mechanism rather than treating the socket or binary as proof.

For each request, the enforcement process should:

1. Authenticate the local OS peer before constructing cloud clients or making any cloud/API request.
2. Load or validate the current protected policy and bind caller identity, configured cloud/project, selected target, allowed operation categories, policy identity, finite limits, and correlation to a server-owned context.
3. Reject missing, stale, revoked, malformed, or out-of-scope authority before any diagnostic implementation/authentication/API call; record a safe denial when the audit store is available, otherwise expose the audit gap locally without claiming a record exists.
4. Recheck current authority and remaining limits before each read and before result publication. A later response-scope failure must describe any prior contact honestly and withhold unsafe data.

A mock caller identity or in-process role check is useful for logic tests but cannot prove that an unauthorized local OS principal is denied. G1 remains open until a separately authorized target-OS test exercises allowed and unauthorized non-root contexts, credential/state access denial, and zero diagnostic/API calls on pre-dispatch denial.

The approved configuration source and credential format remain deployment decisions; no account name, endpoint, path, credential, storage technology, or privilege grant is chosen by this document.

Startup/use must fail closed if trusted scope, protected setup, current policy, or a finite usable limit is missing or invalid. A local readiness check must not silently perform a name lookup or cloud connectivity probe. G2 is not satisfied by synthetic fixtures or a successful local build.

### 4.1 Destination and transport constraints

- Maintain a server-side allowlist containing only the operator-configured Keystone identity destination and the reviewed Nova and Neutron service destinations needed for the enabled operation. No request parameter, model content, resource response, pagination URL, or redirect may add or replace an origin.
- Treat HTTPS with certificate validation and a reviewed trust source as the candidate transport. Do not disable certificate verification. If the target environment cannot support the reviewed transport, keep collection disabled pending an explicit security review; do not silently add an exception.
- Do not inherit ambient proxy behavior or credentials. In particular, do not use proxy environment variables, default environment-derived SDK authentication, caller-selected transports, or implicit auth/profile fallback. Configure transport behavior explicitly.
- Disable redirects for authenticated requests. Reject any response/pagination link that changes the approved scheme, host, port, or permitted service path; never forward a token to a new destination. Apply finite request deadlines, retries only for explicitly safe transient cases, response-byte limits while reading, page/record caps, and cancellation throughout collection.
- A token/service catalog may not expand the trusted destination set by itself. Validate any selected service endpoint against the operator-configured allowlist before sending credentials or requests. Denials, TLS errors, timeouts, malformed links, and reader-policy failures stop the operation without fallback.
- Keep the configured project and selected target in server-owned authorization context. Verify returned identity/relationships before every subsequent read; do not treat a successful API response or common resource name as a grant.

G3 review should inspect the actual SDK/HTTP transport defaults (including proxy and redirect behavior), authentication construction, service-catalog handling, pagination, token handling, and returned identity checks. Synthetic HTTP tests can establish request order and rejection behavior, not actual cloud reader permissions or deployed policy.

## 5. G4 candidate: protected versioned state and fail-closed ordering

### 5.1 Namespace, creation, and durability

Use a new protected namespace, separate from every legacy investigation, memory, workflow, and project store. An explicit format/version marker is required. The operator-selected data root and version name are not chosen here. Never read, import, index, send, modify, delete, clean, or reuse approvals from legacy stores. Refuse corrupt, incompatible, unsafe, or uncertain state; do not auto-repair it or claim it was saved.

A candidate Linux filesystem sequence, subject to target-filesystem review and fault tests, is:

1. Open the operator-configured root relative to a trusted directory handle; verify ownership, restrictive permissions, expected directory/file types, and no symlink traversal. Do not follow untrusted replacement paths.
2. The operator exclusively provisions the namespace directory and protected lock directory with restrictive permissions, then synchronizes their parents; the runtime synchronizes the namespace directory after its initial contents are durably installed. The initialization and operator promotion rules in §5.3.1 apply. If required directory synchronization is unsupported or fails, keep admission closed.
3. Before enabling dispatch, initialize the namespace manifest and required bounded shared control state with exclusive handle-relative creation and no-follow semantics, complete writes and required file/directory synchronization. Create each bounded operation record/control file as needed under the namespace lock using the selected two-bank record protocol in §5.3.4; do not preallocate a fixed pool. Include such creation/allocation in the applicable capacity bounds, and do not claim success after a short write, failed sync, failed rename, or uncertain result.
4. Reopen and validate format, integrity, scope, permissions, and recovery state before admission. No automatic schema migration or fallback to a legacy path is permitted.

Exact syscall choices, filesystem/mount support, directory layout, ownership, and durability guarantees require G4 review. File sync plus rename alone is not evidence of durable directory entries. If the selected filesystem cannot meet and demonstrate the required ordering, do not enable persistence-dependent diagnostics.

### 5.2 Writer, admission, health, and lock ordering

A Level 1 candidate is one exclusive cross-process namespace lock shared by admission, health transitions, record writers, and cleanup. Always acquire that lock before reading/modifying durable health, managed-capacity accounting, intent/outcome records, recovery acknowledgements, or cleanup state. Do not acquire a second store lock beneath it or call a helper that reacquires it. Bound lock wait; contention, lock corruption, or lock timeout rejects the request without cloud authentication or API calls.

Under the lock, verify store version/integrity, current health/recovery state and trusted configuration. Before each credential-bearing authentication or API dispatch, perform the current MVP available-capacity check described in §5.3.4, persist the durable attributable intent, and recheck capacity immediately before dispatch. The check is not a reservation; any failed or ambiguous intent write prevents dispatch. Persist and synchronize the intent before dispatch. Keep admission serialized through the bounded read and durable result/outcome record. Release no result to the caller until its sanitized outcome is durable. A simpler single-writer policy sacrifices parallel throughput but avoids conflicting admissions/writes; any alternative must document and prove an equivalent cross-process ordering.

If a process exits while holding the OS lock, the lock may be released by the OS, but the durable pending intent must remain visible. On restart, an unresolved intent or uncertain outcome is not a healthy state: refuse new dispatch until recovery is explicitly handled. A volatile mutex/latch, process restart, or missing health marker cannot clear uncertainty.

### 5.3 Capacity, audit, result, and recovery sequence

Require an operator-supplied finite usable managed-data limit before use. Account for managed records and sanitized audit/control/recovery metadata. Before each credential-bearing authentication or API dispatch, perform the available-capacity check in §5.3.4 against finite bounded record/control needs, remaining managed capacity, available filesystem bytes/inodes and applicable detectable quota. Refuse if any required value is missing, insufficient or unverifiable. This point-in-time check is not a reservation or guarantee. Distinguish managed-limit exhaustion, quota exhaustion and actual filesystem/inode exhaustion; any later write/sync/device failure remains fail-closed.

For each admitted operation:

1. Before accepting requests, complete the startup order in §§5.3.1–5.3.2/5.5 with the namespace lock held as a session lease. Authenticate the local peer and derive current authorization; reject invalid requests before any cloud/API call.
2. Under that already-held lock, validate durable health, version, current scope, finite bounds, managed accounting and the available-capacity check. If any mandatory control is unavailable, fail closed.
3. Sanitize and durably persist attributable intent before each credential-bearing authentication or API dispatch. Recheck available capacity immediately before dispatch. A failed or ambiguous intent write or unavailable/insufficient check means no dispatch.
4. Perform only the admitted bounded read(s), checking current authorization, relationships, cancellation, and remaining limits between operations.
5. Minimize/sanitize the response before every sink. Verify returned identity/relationships before subsequent reads or disclosure.
6. Durably persist the safe outcome/status, timing, correlation, required provenance, and audit result before returning any diagnostic payload. If outcome persistence fails after a read, stop later dispatch, withhold the payload, expose the possible prior read and audit gap locally, and leave admission unhealthy. Never claim that a read was rolled back.

A denied request with an unavailable audit store must be rejected without a reader call and must visibly report that no durable denial record could be confirmed. Do not fabricate an audit event, retry an ambiguous append as though it definitely failed, use an unprotected fallback sink, or report a saved result without durable confirmation.

### 5.3.1 Reviewable G4 refinement: identity and initialization

This refinement is a candidate, not proof of Linux or filesystem behavior. The operator must establish a trusted root and every ancestor from a trusted starting directory: directory ownership and modes/ACLs must prevent untrusted creation, rename, replacement, and traversal; the credential owner must not be able to modify operator-controlled ancestors. Reject unexpected owners, ACLs, mount changes, hard links, types, modes, or scope. Traverse by directory file descriptors using Linux `openat2` with `RESOLVE_BENEATH`, `RESOLVE_NO_SYMLINKS`, and `RESOLVE_NO_MAGICLINKS`, or an independently reviewed equivalent; fail closed if the required semantics are unavailable. Do not resolve a previously checked pathname again for use.

The operator provisions the namespace directory beneath that root, protects its parent against runtime replacement, and synchronizes the parent before making it available. The runtime may create only the designated contents inside the validated namespace directory. A durable initialization manifest binds format version, namespace identity, authorized scope and integrity checks to the initialized objects. Publish it only after all required objects and directories are completely written and synced. Existing namespaces are reopened, never treated as fresh merely because a manifest or file is absent. Missing, partial, incompatible or ambiguous initialization requires operator intervention with admission closed; no automatic repair or legacy lookup. For new files use handle-relative exclusive creation (`O_CREAT|O_EXCL|O_NOFOLLOW`), validate regular type, owner, mode and link count, loop over bounded short writes, sync file, rename within the same directory and sync that directory. A failed or ambiguous rename or sync is not success: reopen and validate all relevant entries and durable state under the lock; if the outcome cannot be established, refuse admission.

**Provisioned lock and bootstrap trust chain.** Before any runtime starts, the operator creates and syncs one regular lock file in an operator-controlled directory, syncs that directory and its parent, and provides its namespace identity, expected device/inode and the identity of the pre-provisioned namespace directory through independently protected configuration. The credential-owning principal may open the lock for locking but cannot write, unlink, rename or replace it, modify its directory or ancestors, or change that configuration. Validate ownership, modes and ACLs, file type, single link, device/inode and mount identity through trusted handles; a writable parent or unverifiable trust chain closes admission. No runtime process creates or replaces this lock. The same provisioned lock is both bootstrap and namespace lock; there is no second lock or manifest-dependent bootstrap identity.

Every process opens that exact entry handle-relatively without following links, compares its descriptor with the trusted configuration and directory entry, and obtains a bounded exclusive `flock`. After acquisition and before each admission, revalidate the descriptor, entry, namespace directory and protected ancestors; hold the descriptor and lock through initialization, admission, writes and publication. A timeout, mismatch, unavailable check or unsafe replacement closes admission. Inode checks are not a defense against a principal that can replace the object: exclusion of such principals for the entire lock lifetime is a mandatory operator-enforced prerequisite. Process death releases the OS lock, not the durable state; the next holder must reconcile before admitting. Operator maintenance or replacement requires stopping all holders, closing admission and performing a separately reviewed operator-controlled reprovisioning procedure; this design never switches lock identity while a process may hold the old one.

**First creation and reopen.** Under the provisioned lock, trusted initialization-only configuration permits creation only in the verified new, empty namespace. Create and sync all required objects, including a distinct initial `BOOTSTRAP` session-control generation and its specified initialized inactive bank, before publishing/syncing the manifest and its directory. The manifest binds the exact initial control identity/generation and initialized layout to this namespace, scope, version and lock; `BOOTSTRAP` is not `CLEAN` and has no session predecessor. Initialization-only mode never admits requests or cleanup. Concurrent initializers share that lock; the second may only validate completed initialization or refuse uncertainty, not reinitialize.

With runtime holders stopped, the operator validates successful initialization under the same lock before durably promoting independently protected configuration to existing-namespace mode, binding the exact initialized manifest and bootstrap identity. The runtime cannot promote, revert, or renew first-start authority. Promotion authorizes at most one deliberate first launch: the operator establishes protected, durable consumption of that authorization before allowing the selected launch to attempt `ACTIVE`, with no automatic restart using the same authority. The selected holder also verifies the exact initial banks, inventory, protection and bindings under the lock. A later holder with only `BOOTSTRAP` and a consumed, missing or uncertain first-start authorization pauses, even if the failed first `ACTIVE` attempt left no differentiated bytes. Interrupted initialization, promotion or first start requires controlled operator validation and, for a possible session attempt, reconciliation and durable acknowledgement scoped to the attempted startup and identifiable session. A validated bootstrap can still anchor a deliberate recovery `ACTIVE`; this is not a retry of initialization. Missing/corrupt/partial/incompatible or ambiguous existing state does not qualify, even if the directory looks empty. Never automatically recreate files, roll back promotion, replace the lock or consult legacy state.

### 5.3.2 Reviewable G4 refinement: recovery and audit units

Each separately dispatched lookup, resource read, related operation, and bounded page or retry subcall has its own sanitized durable intent identifying request/correlation, parent relationship, scope, operation and finite subcall budget. Authentication and any other separately dispatched credential-bearing operation are covered before contact as well. This clarifies task §6.2/V8 and ADR B3; it is not a new product permission. A parent intent does not authorize unbounded or unattributed subcalls. Revalidate authority and remaining limits before each dispatch; revocation stops subsequent calls, attempts cancellation and prevents unauthorized disclosure.

Under the shared lock, the durable journal/control state must support these transitions: initialized/healthy → capacity checked and durable intent → dispatched-or-uncertain → durable sanitized outcome; only a validated outcome and current disclosure authority permit release. The check is not a capacity reservation. Since local storage cannot atomically record remote dispatch, any durable intent without a verified durable outcome is potentially dispatched, including a crash before the actual call. A failed or ambiguous intent write prevents dispatch; reconcile its exact identity on restart without blindly appending it again. A failed or ambiguous post-read outcome, failed marker write, process death, corrupt record, or unresolvable partial write leaves the namespace paused. A missing fault marker never establishes health. Reopen under the same lock, validate all record/control state and reconcile intents, outcomes, managed charges and cleanup before shared admission; any unclassifiable state remains closed and locally visible.

**Restart-visible session witness.** Use the existing exclusive namespace lock as a process-lifetime session lease. A second process refuses while it is held; helpers do not reacquire it. Before writing `ACTIVE`, validate the trusted bindings, current policy and required control/inventory, and check available filesystem bytes/inodes, managed headroom and applicable quota against the complete finite bound for this transition. Refuse if any required check is unavailable, insufficient or ambiguous. Durably commit a fresh `ACTIVE` linked to the validated start state before the first required startup-cleanup write, diagnostic/audit-requiring CLI/IPC request (including denials), or credential construction. Failure or ambiguity establishing `ACTIVE` means none of that work starts; report the refusal locally independent of the store. Do not fall back to `BOOTSTRAP` or an older `CLEAN` on uncertain session control. An unchanged predecessor alone does not prove that no later start was attempted. Purely local help/readiness without a lease may do no lookup, credential construction or diagnostic action.

**Startup and restart decision under the same lock** (takes precedence over ordinary bank selection):

| Established state | Required action |
| --- | --- |
| Exactly initialized and promoted `BOOTSTRAP`, with the protected first-launch authority from §5.3.1 | Commit first `ACTIVE` against the exact bootstrap generation; do not invent a prior session or `CLEAN` certificate. |
| Exact linked `CLEAN` is the highest unambiguous control generation and meets the restart durability rule below | Verify all required records/control with no unresolved intent, gap, cleanup or recovery reference. Start a new `ACTIVE` under current policy, not by reusing the prior session. |
| Stale `ACTIVE`, unproven/mismatched `CLEAN`, uncertain start, or missing/corrupt/incompatible/ambiguous control | No automatic admission or cleanup. Preserve the last established witness and unresolved links; report prior-session uncertainty locally without claiming a saved event. Reconcile established state under the lock, obtain durable acknowledgement scoped to the affected session or identifiable startup attempt, resolve store faults and revalidate current policy before deliberate fresh `ACTIVE`. Do not label the uncertain close orderly. If identity, acknowledgement, accounting or integrity cannot be established, stay paused. |
| Fresh durable `ACTIVE` established by this holder | Run bounded startup cleanup under the same lease as in §5.5 before opening request admission. A required-write failure leaves this witness in place, closes admission and stops work; report the local gap and never write `CLEAN` to mask it. |

A `CLEAN` certificate binds the namespace, exact preceding durable `ACTIVE` generation and session identity, and its own generation. Write it only after work ends with no known gap and all required outcomes and cleanup transitions proven durable. For restart, require proof of that exact close under §5.3.3: validate both banks, the exact link and highest unambiguous generation; sync the session-control file and any required directory metadata, then reread and compare the same certificate, predecessor and proof under the lock. A later successful sync and reread do not supply missing proof. If a prior close error is known, stay paused for reconciliation and scoped acknowledgement even if persistence can be established; if a failed and an orderly close are indistinguishable under the supported model, use the paused branch. A verified orderly close preserves the healthy path. Session-scoped recovery records may link a deliberate new `ACTIVE` to the reconciled session without claiming that it closed cleanly. If recovery or acknowledgement is interrupted, preserve the prior witness and require positive durability proof again on restart.

Once `ACTIVE` is durable, a denial-audit, initial pre-intent or startup cleanup-intent write failure, even with no changed intent bytes and no writable post-failure marker, leaves the existing witness. Stop work and exit without `CLEAN`; OS release of the lease does not erase `ACTIVE`. A later holder pauses despite healthy-looking ordinary records. Acknowledgement is not a reconstruction, disclosure authorization, consent to recollect or replay. Include all applicable start/close/recovery, durability-evidence and acknowledgement writes in the complete finite dispatch and cleanup bounds.

If the first capacity check passes and the intent is durably committed but the immediate pre-dispatch check refuses, do not issue that dispatch. When the store permits, persist and confirm a sanitized terminal outcome tied to that intent that records `not-dispatched` for this operation and the safe refusal reason. This establishes zero dispatch for this operation only; it does not erase or misstate earlier authentication/read activity in the parent request. If this outcome write or sync fails or is ambiguous, retain the intent as unresolved, expose the audit gap through a local path independent of the store, and pause admission across processes and restarts. Do not claim from an unavailable or ambiguous record that the call did or did not occur, fabricate an outcome, or retry the write as though it definitely failed. Reconcile the exact intent/outcome under the shared lock before reopening; until then apply the ordinary unresolved-intent rule and do not replay. A successfully confirmed terminal outcome permits an honest denial result, including any possible prior calls in the same request.

For each identified gap or uncertain call, persist a scoped operator acknowledgement with its own identity and durable commit before considering it acknowledged. Failed or ambiguous acknowledgement writes leave the gap unacknowledged until safely reconciled; restart never infers acknowledgement. Reopen admission only after storage faults are resolved, all known gaps are durably acknowledged and integrity/current policy checks pass for all processes; repeat the MVP available-capacity check before each later dispatch. Acknowledgement neither fabricates an outcome nor grants authorization, releases a result, replays a call or confirms recollection. If the minimally retained payload is unavailable, report that fact; a new observation requires separate explicit confirmation, current authorization and a new timestamped intent. Local gap reporting must not depend solely on the failed store.

### 5.3.3 Historical pre-amendment G4-03 capacity guarantee and retained record protocol

The former guarantee-based capacity mechanism and its infrastructure/preallocation prerequisites below are historical only and are not MVP requirements. Section 5.3.4 explicitly adopts the bounded two-bank record encoding, generation/integrity update and restart-recovery rules described here as the current candidate record protocol, while excluding the former fixed slot-pool reservation/accounting model, preallocation, no-allocation-after-dispatch, dedicated-filesystem and reserved metadata/journal assumptions. The historical pool-sizing formulas and reservation transition table below do not define current managed accounting; §5.3.4 does. Where this section conflicts with §5.3.4 on allocation, admission capacity or cleanup, §5.3.4 governs.

**Capacity mechanism proposed for the historical G4 review.** Use a finite pool of fixed-size operation slots and cleanup-control slots, all created, fully allocated, initialized and synchronized before the namespace is admitted for dispatch. The pool resides on a dedicated local filesystem or equivalently isolated fixed-capacity volume used only by this protected store; the runtime has no authority to create files, extend the volume, change quotas, snapshots or mount options. Exclude copy-on-write/reflink, snapshots, compression with dynamic allocation, thin provisioning, deduplication and any other layer that can defer or amplify allocation unless its capacity semantics are independently specified and validated. The supported storage configuration must provide a fixed filesystem metadata/journal capacity whose worst-case consumption for the bounded in-place write-and-sync sequence is documented and reserved independently of the data-slot pool. This is a required prerequisite, not an assumed property of `fallocate`; if that property or the isolation of the volume cannot be established, no dispatch is permitted. No separate per-operation journal reservation is mandated: the proposal is a preallocated data/control-slot pool plus the selected filesystem's fixed, protected metadata/journal capacity. If no supported local filesystem configuration can provide both within the approved privilege and infrastructure boundary, stop and request a Level 2 decision rather than weakening the requirement.

Before each external read, under the shared lock, verify the configured finite managed limit, namespace/filesystem identity and supported mount/quota configuration; reconstruct the slot pool and its allocation/accounting from validated records; verify that at least one fully provisioned slot is available; and confirm that no untrusted or unrelated writer can consume the pool's capacity or change the validated quota/storage configuration. For each supported filesystem, define a finite `M` as the independently documented maximum metadata/log transaction footprint for the serialized intent, outcome, recovery and acknowledgement write/sync sequence, and define `Mcleanup` for the maximum cleanup batch. These bounds must fit within the filesystem's fixed, preallocated journal/log capacity, which is not drawn from the application data-slot pool or its managed quota; all file extents, slot-control objects and directory entries are provisioned before admission so admitted writes do not allocate or extend them. The selected filesystem configuration must keep these fixed capacities available independently of data-slot allocations; the operator-controlled quota/mount configuration must remain immutable while the runtime is active. The runtime verifies the configured filesystem, mount and quota identity before admission and refuses if it changed; it does not treat a free-block/inode snapshot as evidence of `M` or `Mcleanup`. If the filesystem cannot document and maintain these finite bounds, it is unsupported for this design and dispatch/cleanup is refused. Admission capacity is the complete preallocated slot (not a free-space snapshot), plus the separately established fixed metadata/journal budget for the bounded slot-bank updates and syncs. The intent, maximum outcome, recovery/gap state and required acknowledgement must fit the slot's prebounded regions. If any identity, reservation, accounting, quota or filesystem condition is missing, changed, ambiguous or unverifiable, refuse before reader authentication or API dispatch. Managed-limit exhaustion, physical filesystem/inode exhaustion, quota exhaustion (`EDQUOT`) and other write/sync/device failures remain distinct conditions; this mechanism addresses capacity under its stated assumptions and does not claim arbitrary I/O failures are impossible.

All slot and cleanup-control files and directory entries are provisioned and synchronized before dispatch is enabled. During admission and result persistence, update only fixed preallocated regions in place using the two-bank protocol below: no file creation, extension, rename, directory-entry update or allocation occurs after the read is dispatched. Cleanup is likewise bounded and uses the preallocated cleanup-control slot plus fixed-size slot contents: after durable deletion intent, overwrite/clear every bank containing an eligible expired record, including any prior-generation copy, while preserving required unresolved control/audit state; synchronize the affected preallocated files, then persist the bounded cleanup outcome. This is logical deletion within the application store, not a claim of physical secure erasure. Slot files and directory entries remain allocated for reuse; cleanup does not unlink them or claim physical blocks are freed. If a future design requires unlinking or directory mutation to reclaim physical space, it must separately specify and reserve the metadata/journal capacity for that operation before deletion, or refuse cleanup; it cannot rely on data-slot preallocation alone. On any unexpected write, sync or cleanup failure, preserve uncertainty and accounting, stop later dispatch, withhold payload after a read, expose the possible completed read/deletion and audit gap locally, and require reconciliation. No capacity reservation is a claim of rollback.

**Candidate accounting and operation inventory.** Before dispatch, choose reviewed finite maximum encoded bank sizes `C`, `I`, `O`, `R` and `A` for slot control, intent, outcome, recovery and one acknowledgement, including their headers, checksums and padding. For the reviewed maximum `G` gaps per operation, a slot requires `2 × (C + I + O + R + G × A)` allocated data bytes, rounded up for the selected filesystem's allocation units, plus its fixed header and alignment padding; the independent `M`/`Mcleanup` bounds cover the corresponding fixed journal/log transactions and are not counted as data-slot bytes. Each gap has its own immutable identity and acknowledgement-bank pair. Admission requires a bound that covers all gaps the operation can create; if that bound cannot be established, refuse dispatch. If an unexpected overflow is detected after dispatch, stop admission and report unresolved uncertainty locally; never drop a gap or claim it acknowledged. A separate, bounded pre-created cleanup-control slot reserves two banks each for a deletion intent and deletion outcome, large enough for the maximum cleanup batch. The proposed sizes, alignment, gap bound, cleanup-batch bound and actual filesystem charge must be recorded and reviewed before use; these symbols are not selected deployment values.

Create, allocate, initialize and sync the complete finite slot pool and its containing directories before it can be admitted; no per-request creation is allowed. Charge the finite managed limit for every allocated slot, its managed headers/control records and any conservatively accounted metadata allowance, not only occupied payload. The reservation is an exclusive assignment of an already charged slot, not an additional charge for its bytes; retained and reusable slot files remain charged. Reconstruct assignment and charges from validated durable slot identities on restart, conservatively charge ambiguous slots, and refuse if accounting cannot be reconciled. A slot is eligible for reuse only after durable outcome and all required acknowledgements, retention and reference checks; cleanup clears eligible records but does not release their physical allocation. `st_blocks`, free-space snapshots or an application metadata allowance are accounting inputs at most, not proof of a reservation or fixed filesystem metadata/journal capacity.

**Candidate torn-write protocol, subject to filesystem feasibility.** Each pre-created operation slot has separate bounded slot-control, intent, outcome, recovery and per-gap acknowledgement regions; the separate cleanup-control slot holds deletion intent and outcome. Each region contains two independently placed fixed-size banks. Each bank encodes the slot and record identity, type, generation, bounded length, sanitized payload and integrity check. Initial empty banks and their slot identities are written and synced before admission. To update a region under the shared lock, write the next generation completely to the inactive bank, leaving the previously valid bank untouched; synchronize the slot file and confirm success before taking the next externally visible action. No selector is overwritten in place: after restart validate both banks and select the highest valid, unambiguous generation. Invalid lengths, identity conflicts, equal generations with different contents, generation wrap or a bank that cannot be classified close admission. An interrupted update may leave the prior bank valid and the new bank incomplete; never call the incomplete generation committed or overwrite the prior bank to repair it. Checksums detect accidental damage only subject to collision and storage-fault assumptions; they are not authentication or proof of atomic writes. For the adopted MVP record protocol, the restart durability rule below overrides generic bank selection. A failed resync or unexplained or ambiguous state remains closed.

**Current MVP restart durability rule.** This rule applies to exact session/start state, cleanup tombstones, and any required intent, outcome, acknowledgement or release used to advance those transitions. For a write performed by this holder, require complete bounded writes on validated objects, successful required file and directory sync in order, and locked reread/revalidation under a reviewed filesystem/write/sync/integrity model. After handoff, require positive evidence covering the exact generation, content and required metadata: the model must show why the evidence could only be accepted after those bytes and prerequisites reached stable storage, or why a separately authorized new complete transition durably establishes the required state now without inferring success of an earlier failed attempt. Stop on any mismatch, error or missing evidence. Integrity checks validate identity/content within the model, not persistence.

Linux `fsync(2)` documents that many local filesystems report writeback errors to descriptors open when the error was recorded. A new descriptor's lack of that error, readable/page-cache bytes and a bare successful resync plus matching reread do not distinguish persistence from a failed earlier writeback. For example, a later dependent commit can attest to an earlier exact write only if the reviewed ordering forbids its creation before that earlier write was proven durable, and the model also establishes the dependent evidence itself; neither is assumed here. Do not accept an apparent successor or revert to an older healthy-looking bank if the possible failed and completed transitions cannot be distinguished. Keep the prior witness or cleanup intent and charges in force across further restarts; do not overwrite them to make recovery look healthy. A known required-write failure still requires controlled reconciliation and applicable durable acknowledgement, not automatic admission, success publication or reuse. This does not rule out proving completion under a stronger, reviewed model.

### 5.3.4 Current MVP: available-capacity check and accepted failure risk

The approved MVP uses the existing shared local filesystem; it does not require a dedicated filesystem, volume, preallocated journal/log budget, or guarantee that later required writes will succeed. This candidate selects the bounded two-bank record protocol described in §5.3.3 for operation/control records and cleanup control: each bounded record region has two generations, and updates write and synchronize the inactive bank before it can be treated as durable. Record/control files may be created and allocated as needed under the namespace lock; a fixed pool, full preallocation, or a no-allocation-after-dispatch assumption is not required. Apply §5.3.3's bank validation, generation selection and ambiguous/interrupted-update recovery rules as current requirements, except where its historical reservation protocol conflicts with this section. On eligible logical deletion, durably clear every bank/generation containing that record, preserve required intent/outcome and recovery state, and retain the allocated record/control files for reuse; do not claim secure erasure or physical space reclamation. The former fixed-pool reservation, dedicated-filesystem and independent metadata/journal-guarantee conditions remain historical, not MVP admission requirements. Slot sizing, complete writes, sync ordering, retention, restart reconciliation and fail-closed handling remain required; capacity observations do not satisfy or replace them.

**Normative selection and cleanup state (overrides ordinary highest-valid-bank selection while cleanup is pending).** Every logical record has an immutable record identity plus a never-reused incarnation identity; each bank also carries its generation. Before clearing anything, durably commit a cleanup intent that names the exact record identity, incarnation and both observed bank generations, cleanup-batch identity, eligibility/retention basis and bounded scope. Revalidate that exact identity and eligibility under the same lock immediately before clearing. The durable pending intent takes precedence over the ordinary highest-valid-generation rule: during startup and runtime, load cleanup control before selecting records; any record named by a pending intent is unavailable for current read, selection or disclosure even if an older bank still validates. Keep its managed charge and control/recovery state. Unnamed records are unaffected; unknown, active, referenced, unexpired and recovery-critical records remain protected.

For each targeted record, replace each named bank's payload with a bounded integrity-checked tombstone binding exact record, old incarnation, batch, bank and generation being cleared. Count a bank as clear only after its exact tombstone is positively established durable under §5.3.3, including sync and locked reread/revalidation against the durable intent. On restart:

| Observed banks for this intent | Decision |
| --- | --- |
| Both exact tombstones proven durable | Both clears are established. Proceed only with the ordered outcome/release steps below, subject to reconciliation and any required acknowledgement. |
| One exact old bank, other bank proven clear or unproven | Keep the entire target unavailable and charged. Revalidate exact identity, current policy, eligibility/retention and capacity under the lock before a specifically authorized complete tombstone write on the intact old bank. That proves only that bank; do not automatically retry an uncertain batch or infer a clear for the other bank. |
| One or both banks blank, absent, torn, corrupt, invalid or mismatched | Unknown loss, not a clear; even both absent do not establish deletion. |
| Matching visible tombstone after failed/ambiguous write or sync, including errors seen only by the prior descriptor | Count it only with positive §5.3.3 proof. A later successful sync and matching reread without such proof still leave it unproven. |

For any unproven clear, preserve pending intent, visibility exclusion and charges across restarts; report possible logical deletion and the audit gap locally and pause admission for controlled reconciliation and any required scoped acknowledgement. Safe authorized inspection of unrelated validated records remains distinct from diagnostic admission. Never fabricate success. Both proven clears precede the matching sanitized durable success outcome, which precedes the separately durable release/reusable state bound to the old incarnation and batch. Failed/ambiguous outcome, release or required acknowledgement cannot publish success based on uncertain data, expose the target, release its managed-record charge or permit reuse. Do not release until any applicable acknowledgements are proven durable and retention/reference checks pass. Commit a never-reused new incarnation durably before new content; stale intent cannot act on it. Allocated file/inode charges remain; logical clearing does not reclaim physical space or securely erase it.

Each cleanup batch also receives a distinct durable cleanup-audit record, with its own identity and two-bank intent→outcome update. Do not overwrite a prior batch's audit record when reusing the bounded cleanup-control banks or performing a later batch. Retain each audit record for its own configured audit-retention window and while referenced by recovery; only then may it become eligible under the same exact cleanup protocol. If the finite managed capacity cannot hold the required new audit/control records without displacing still-retained history, refuse cleanup and preserve the charge rather than overwrite protected audit. Include the session-control, intent/outcome, clear/reusable-state and retained cleanup-audit writes in the complete finite byte/inode/managed/quota accounting; the separate cleanup-batch check remains additional.

Bind the capacity policy to trusted initialization state, not to whichever values a check happens to observe. During controlled initialization, record in the durable manifest and independently protected operator configuration the expected store/filesystem identity, the identity and configuration revision of any applicable quota association (including its subject and enforced byte/inode limits), and the managed-limit policy identity/revision and finite limit. At each admission check, compare the current store/filesystem identity and applicable quota association/configuration with this trusted binding, and verify that the managed-limit identity, revision and value still match. Bind stable identities and policy, not changing free-space, inode-availability or quota-usage counters: their ordinary consumption changes are capacity readings to compare with thresholds, not identity changes. An observed mismatch, changed policy, missing value or unverifiable identity closes admission pending controlled operator revalidation; never silently adopt the newly observed identity or limit. Revalidation requires admission closed, all runtime holders stopped, unresolved intents/gaps reconciled, the intended configuration reviewed, and a new binding durably committed before reopen; the runtime gains no privilege to alter quota or policy. A change occurring after a successful observation remains the accepted point-in-time race described below, not evidence that the earlier check observed a mismatch.

Before every distinct credential-bearing authentication or API dispatch—including lookup, resource read, page and retry—while holding the shared lock and after current authorization/recovery checks, identify the store directory by its already-validated handle and filesystem identity. Obtain available bytes and available inodes for that filesystem (for Linux, a reviewed `fstatvfs`/`statvfs`-equivalent on the trusted store handle that exposes unprivileged-available bytes/inodes); reject an identity mismatch or unavailable result. Recompute the finite managed limit `L` and durable managed usage `U` from validated store records, conservatively charging incomplete, retained, reusable and ambiguous records; require `U <= L` and available managed headroom. Do not treat filesystem free space, `st_blocks`, or an earlier snapshot as managed-limit accounting.

Derive the complete per-dispatch thresholds from the reviewed finite record layout and operation bounds, not invented deployment values. `Bnext` must cover the maximum additional physical bytes needed for the bounded intent, maximum sanitized outcome, recovery/failure-gap/control state, required acknowledgement, and applicable bounded cleanup-control work; include the selected filesystem's justified alignment/metadata allowance. `Inext` must cover the maximum additional inodes required by that complete work (zero only where the reviewed design demonstrably creates no inode). The corresponding `Mnext` managed-byte charge and applicable quota byte/inode thresholds must cover the same complete bound. Derive a conservative peak bound: aggregation may avoid double-counting only where non-overlap is demonstrated, and no applicable operation, recovery, acknowledgement or cleanup-control need may be omitted. Apply the complete thresholds consistently to available filesystem bytes/inodes, remaining managed capacity and applicable quota. The separate capacity/identity check before each cleanup batch remains mandatory and does not substitute for including applicable cleanup-control needs in the per-dispatch threshold. Require available filesystem bytes `Fbytes >= Bnext`, available inodes `Finodes >= Inext`, remaining managed capacity `L-U >= Mnext`, and applicable quota headroom sufficient for the corresponding byte/inode charges. Use overflow-checked arithmetic and refuse if a bound, charge or threshold is absent or cannot be computed. Before enabling the store, the operator-reviewed finite limit, slot/record maxima, gap count, cleanup batch/control bound, alignment and accounting method must be specified; no numeric values are selected by this manual.

Determine quota applicability from protected operator configuration and the filesystem actually containing the store. Compare the current quota association/configuration identity and enforced limits with the protected initialization binding before using its remaining allowance. If a quota applies and its current remaining byte/inode allowance can be queried, require it to cover the same next-operation charges. If quota is configured, may apply, or cannot reliably be ruled out but its identity, state or remaining allowance cannot be queried, refuse dispatch. A detected quota shortfall (`EDQUOT`), managed-limit shortfall, filesystem byte/inode shortfall (`ENOSPC`), and other I/O/sync/device errors remain distinct outcomes. The check is repeated immediately before every dispatch, but does not reserve capacity. A competing filesystem consumer can consume space between check and write; operator quota/mount configuration can change; snapshots, reflinks, compression, thin provisioning or other allocation layers can change effective capacity; and writes/syncs can fail later or report delayed errors. Do not claim these races are prevented by the shared lock, which only serializes this store's cooperating processes.

Sequence for each dispatch: (1) under the shared lock, revalidate the trusted store/filesystem, applicable quota and managed-limit identity binding, current authorization, recovery health, finite bounds, managed accounting, available bytes/inodes and detectable quota; (2) durably persist that dispatch's sanitized intent, refusing dispatch on any failed or ambiguous write/sync; (3) repeat the identity and available-capacity check immediately before the external authentication/API call; (4) dispatch only if the second check succeeds. If step 3 refuses, apply the terminal not-dispatched outcome and unresolved-write behavior in §5.3.2. Every independently dispatched auth, lookup, read, page and retry gets its own intent and check. Outcome persistence remains mandatory before disclosure. If a write/sync fails after a read may have occurred, stop all later dispatch across processes, withhold the payload, expose the possible read and audit gap locally without relying on the failed store, preserve restart uncertainty, and require recovery and durable acknowledgement. Never claim rollback, fabricate an audit record, replay automatically, or treat the capacity check as a write guarantee.

Cleanup uses its bounded durable intent before clearing eligible records and its durable outcome afterward. Before each cleanup batch, compare the same trusted filesystem, applicable quota and managed-limit identity binding used for dispatch; then check available bytes/inodes, managed headroom and applicable quota for the bounded cleanup writes. If the binding or any check is unavailable, mismatched, insufficient or ambiguous, perform no cleanup and keep admission closed pending controlled revalidation where identity is in question. If clearing or outcome persistence fails, preserve uncertainty and recovery records, report possible logical deletion and the audit gap locally, and do not release managed charges or silently retry. Under the selected two-bank record layout, clear both generations in every eligible record region while preserving cleanup intent/outcome, any shared control data and recovery-required records; retain the bounded record/control files for reuse. Logical clearing is not physical secure erasure or a claim of physical block reclamation. Actual target-filesystem, independent-process, crash, quota and bounded-ENOSPC tests remain required later under separate authorization; this design makes no claim those tests have run or that the check guarantees success.

### 5.4 Minimal payload retention

The candidate retains only the minimum sanitized intent, scope/policy identity, status, timing, safe error/gap, and provenance needed for audit and recovery. It does **not** retain a full diagnostic payload by default. Keep a sanitized result in process memory only long enough to commit its durable outcome; disclose it only after that commit. If the process crashes or the payload cannot be safely recovered, report the unresolved/uncertain read honestly. Recovery acknowledgement is not authorization or consent to recollect; a new collection requires separate operator confirmation, current authorization, and a new timestamped observation. This choice reduces retained sensitive data but means an interrupted result may be unavailable and need an explicitly authorized new read.

### 5.5 Cleanup and retention

Cleanup is bounded by explicit record, byte, and time limits, and runs only during startup/operation—not while the runtime is stopped. At startup, validate trusted state under the provisioned lock, resolve the bootstrap/restart branch in §5.3.2, and establish durable `ACTIVE` before the first required cleanup write. Run the bounded startup cleanup with admission still closed; only a healthy startup following that step may admit requests. Inability to establish `ACTIVE` permits neither cleanup writes nor diagnostic dispatch. Delete only known eligible records under current retention rules; protect unresolved recovery state and unknown, active, or referenced data. The PRD’s configurable 90-day sanitized-audit default applies to audit records. The 30-day terminal-investigation default applies only when such records are introduced; this manual-only candidate does not invent investigation records or lifecycle.

For each automatic cleanup batch, use the already-held session lock (do not reacquire it) and compare the trusted filesystem, applicable quota and managed-limit identity binding before checking available bytes/inodes, remaining managed capacity and applicable quota for the bounded cleanup work. On identity mismatch or unverifiable binding, close admission pending controlled revalidation; if any capacity check is unavailable, insufficient or ambiguous, do no cleanup. Then durably commit the exact-incarnation deletion intent before clearing both generations. While that intent is pending it governs visibility: the target is not selected from a still-valid older bank and remains charged. Revalidate eligibility and establish both clears under §5.3.4, durably commit the matching outcome, then durably commit release/reusable state before any new incarnation can use the slot. Any interruption or ambiguous sync leaves the target unavailable and charged until the exact intent, generations and outcome are reconciled; unexplained missing/corrupt state is not treated as completed deletion. Failed or ambiguous intent clears nothing. If the first startup cleanup intent write fails with no durable intent or post-failure marker, report the gap locally without claiming a saved audit, keep requests closed and exit leaving `ACTIVE`, not `CLEAN`. The next holder pauses on that session even if other records are healthy; no automatic retry or admission. Reconcile, durably acknowledge the scoped gap and revalidate current policy and store health before deliberately establishing fresh `ACTIVE`. Failed outcome/release reports the gap and possible completed logical deletion without rollback or premature reuse; the exact durability and accounting rules are in §5.3.4. Keep each batch's audit in a distinct two-bank cleanup-audit record for its own retention window; never overwrite an earlier unexpired or recovery-referenced cleanup audit when reusing control banks. If capacity is insufficient for retained audit/control history, refuse the batch. Bounded record/control files remain allocated for reuse, so cleanup does not claim physical blocks are freed. Never silently delete unexpired data to free capacity, delete audit records before their retention period, or touch legacy data.

1. **Before startup/use:** the operator supplies and protects trusted project-reader configuration, approved destinations, credential source, data area, and finite storage limit. Confirm required G1/G4 reviews and G2 setup; keep diagnostics unavailable if any mandatory control is absent.
2. **Before enabling a manual entry point:** complete the separately reviewed G1 realization and actual unauthorized-local-caller OS proof. Before enabling a collector, complete G3 review of API relationships, reader visibility, authentication, and transport. Before persistent execution, complete G4 review and the required implementation safeguards. In the running owner, validate bootstrap/restart under the lease, establish durable `ACTIVE`, then run bounded startup cleanup before accepting requests (§§5.3.1–5.3.2/5.5).
3. **At request time:** authenticate the local caller; derive current scope from protected configuration; validate the exact target and allowed category; check available bytes/inodes, managed capacity and applicable quota, persist attributable intent, then repeat the capacity check immediately before each reader/API dispatch. Help/readiness must not perform diagnostic lookup.
4. **During collection:** use only the reviewed fixed API operations, bounded transport, and verified server-derived relationships. Recheck authorization and budgets between calls. Never escalate credentials or follow a redirect/pagination link outside the fixed destination policy.
5. **Before returning evidence:** minimize and sanitize first, persist the outcome/audit durably, then release the result. Show missing/denied/unavailable fields and collection limitations explicitly; do not call missing evidence healthy or assert a root cause without supporting evidence.
6. **On store/audit/capacity failure:** stop new dispatch and withhold any result whose required outcome is not durable. Report whether a read may already have occurred and whether an audit gap exists. Do not retry an uncertain operation automatically.
7. **After recovery:** remain paused until the operator acknowledges known gaps/uncertain calls. Recheck current policy; acknowledgement restores neither authority nor permission to recollect. An uncertain new read requires separate confirmation and a new timestamped observation.
8. **Cleanup:** perform only bounded, audited cleanup of known eligible data while running; report failures and possible post-delete audit gaps. Never clean legacy stores or silently evict unexpired records.
