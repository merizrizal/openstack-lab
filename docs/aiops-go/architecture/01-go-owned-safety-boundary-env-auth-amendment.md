## 2. Approved decision and narrow boundary

For the new Go manual diagnostic path, OpenStack authentication inputs come only from the Go process environment as supplied by a trusted operator-controlled launcher. Go does not itself search for or load `.env`, and it must not obtain authentication credentials or fall back to them from `clouds.yaml`, `secure.yaml`, or another profile. It does not invoke the root Makefile to obtain environment values. Any separate trusted noncredential policy/configuration source remains governed by the parent ADR/task; U4 neither authorizes a new source nor permits credentials from that source.

Environment inputs are authentication material, not authorization policy. Preserve the approved identity and scope: the fresh restricted application credential for `aiops-assistant-project-reader`, project label `admin` (not administrator authority), domain `default`, `reader`-only access, one-month expiry, and OpenStack admin-team rotation/revocation ownership. The authenticated principal and project must be checked against trusted application policy before any resource read. The environment cannot expand tool, target, project-wide, budget, audit-path, or approval authority. Authentication, identity, project, or policy failure has no stronger-credential fallback.

This is a narrow Go-specific exception to profile-based credential loading. The existing revised/Python identity and profile contracts remain unchanged for their own runtimes. This amendment neither authorizes reading nor changing their protected profile files.

## 3. Required engineering constraints

1. Select the pinned Gophercloud v2.14.0 application-credential **ID form**: the only authentication inputs are `OS_AUTH_URL`, `OS_APPLICATION_CREDENTIAL_ID` and `OS_APPLICATION_CREDENTIAL_SECRET`, each required and nonempty. The ID and secret authenticate the restricted credential using Keystone v3; Keystone supplies its implicit project scope. Do not send explicit scope or fall back to v2. Reject other authentication selectors, including credential name, username/domain, user ID, password, passcode, project/tenant aliases, system scope and token inputs, before authentication. The helper reads broader inputs and does not read `OS_TOKEN`; a future implementation may use it only behind checks proving no unsupported input can influence authentication, or construct explicit options. Reject missing, malformed, conflicting and unsupported inputs before any auth call.
2. The accepted authentication source is the process environment—not a Go dotenv loader or credential profile. Do not read, log, copy, print, or embed local `.env` values. The existing development example is not evidence of the dedicated reader identity and must not be used as a production diagnostic credential source. Any separate noncredential policy/configuration source must satisfy the parent ADR/task and must not supply or override authentication inputs.
3. Validate the configured authentication endpoint against trusted approved deployment context before sending credentials. After authentication, verify the authenticated principal and project against independent trusted policy before resource requests; the implicit project scope is not supplied by environment selectors. Service endpoints, region/interface selection, targets, policy, budgets, capability definitions, audit paths, and approval state are not ambient environment overrides or public request inputs; they remain under the approved trusted configuration/owner boundary.
4. Environment variables must not cause credentials to be sent through proxy settings, redirects, or unapproved endpoint origins. Retain collection-time response-byte bounds and destination validation for authentication and service requests.
5. Actual credentials never appear in arguments, logs, errors, results, audit, reports, fixtures, or model input. Use synthetic credentials and canaries only in fixtures; canaries must not reach argv, logs, errors, results, audit, reports, or child/model environments. No model or child process receives OpenStack authentication variables. Existing Go Codex/Pi environment filtering is a relevant observed seam, not acceptance evidence; add regression tests that prove the invariant.
6. Do not change identity, role, project, expiry, rotation, audit retention, legacy profile layout, or deployment authority as part of this source change. Live effective-policy acceptance remains separately gated.

The pinned SDK also supports name plus secret with user ID, or username plus domain; those forms are not selected here. Its request builder gives password/passcode precedence and its helper reads alternate selectors, so rejecting conflicts is mandatory rather than relying on SDK precedence. An issued token is authentication output, not an accepted token-input mode. Offline fixtures cannot prove effective cloud-side role or expiry.

## 4. Architectural consequences and alternatives

The approved preference removes YAML profiles as a Go authentication-credential source. The owner selected a **separate noncredential policy file** at proposed fixed path `/opt/openstack-ai-ops-assistant/policy/diagnostics.json`, under a `root:aiops_assistant` `0750` policy directory; the regular non-symlink file is `root:aiops_assistant` `0640` and not writable or replaceable by the runtime. Validate relevant path components and metadata. A trusted operator or security administrator manages the file; Go uses a closed JSON schema and the Go standard library, not environment, caller/model values, credential-profile contents or catalog responses as policy. No file creation, installation, credentials, new parser dependency or live action is authorized by this draft.

The policy must identify independently confirmed canonical user and project IDs, expected identity/domain labels, approved authentication and service endpoints, permitted server IDs and grants. Default deny: project summaries need a distinct grant; exact-name resolution needs a separate scoped grant. If granted, a bounded exact-name search within the fixed project may receive limited metadata for servers outside the permitted ID list; minimize it, reject ambiguous matches, and make no further read unless the resolved ID is permitted. Without the resolution grant, require a UUID and make no name search. Exact reviewed schema fields and internal mechanisms remain implementation choices, not a new public override.

A trusted operator updates policy atomically and may remove or disable access; additions or changes to fixed identity, project, endpoints, routes or exception scope require applicable security-owner review and approval before installation. Each policy is valid for at most 30 days from issuance, requires deliberate operator renewal, and is revalidated before each credential-bearing operation and related lookup. Missing, unsafe, invalid, expired, revoked or incompatibly changed policy, or inability to establish reliable time, stops further contact without automatic retry or readmission. An already-sent request cannot be undone; retain cancellation and truthful audit obligations. Credential rotation and policy renewal remain separate. Expected user/project IDs and protected endpoint values must not enter Git, logs, audit or reports; no actual values are recorded here.

The owner reported administrative confirmation of the IDs and endpoints, but independent provenance remains unverified. No policy file or actual approved service endpoint list was inspected or established, nor is deployed policy currentness proven. The OpenStack admin team must confirm values through its protected procedure independently of the authentication environment before real values are relied on; a copied environment value is not independent authority. Keep live access disabled pending that evidence and the separately authorized live gate. These unverified deployment facts do not themselves block independent specification review or, after exact-candidate approval/commit, fresh preflight and separately authorized offline implementation using synthetic policies, identities and endpoints with fake/local transports. All policy validation and fail-closed requirements apply to those fixtures; no actual policy, credentials or cloud access is authorized by this distinction. The trusted launch environment remains part of the Go authentication boundary; same-user inspection and accidental child inheritance remain risks. Offline fixtures do not establish effective reader privileges or deployed policy.

The foundation contract records an initial HTTP Keystone endpoint, while the prior U4 task candidate required TLS controls; the existing local exception covers SSH host verification only. The owner selected an HTTP exception and accepted its credential-exposure risk, confirming its scope: Go Delivery 1 application-credential authentication over the documented management path from `assistant02` to the initial Keystone endpoint `http://192.168.121.5:5000/v3`.

The owner subsequently reported that TLS is not currently available for the required service APIs and explicitly accepted the risks of token interception, service impersonation and manipulated diagnostic results for the MVP. A **separate** service HTTP exception is limited to Go Delivery 1 calls from `assistant02` to individually approved endpoints required by the three diagnostics, over operator-approved management routes in this lab. It does not authorize other services, destinations, routes, environments or legacy runtimes. The exact service endpoints and route evidence have not been independently established; the policy and separately authorized live acceptance must verify them. Do not infer destinations or routes from catalog responses. The token-creation path beneath the approved Keystone base is not a grant to follow redirects or contact a different endpoint.

Both narrowly scoped HTTP exceptions expire at **2027-02-07 17:11 UTC**. At or after that instant, or when reliable time cannot be established, deny affected HTTP calls unless a separately approved, time-bounded extension is in force. Policy renewal cannot extend an exception. The OpenStack admin team owns tracking the later TLS migration; the trusted operator/security administrator owns policy updates and applicable security approval. No live use, route change or deployment is authorized.

**Risk evaluation:** HTTP provides no confidentiality, server authentication or integrity. An observer can capture the application credential or token; an active attacker can impersonate Keystone or a service, forge purported identity/project or catalog responses, and manipulate diagnostic results. Independent expected policy and origin checks cannot authenticate a peer over HTTP or eliminate these risks. Reader scope, expiry and revocation limit impact but do not prevent interception or impersonation. Confidential authenticated TLS is safer. Preserve destination, proxy, redirect, bounded-response, audit, identity and no-fallback controls; keep live use disabled pending the separate acceptance gate.

Level 1 implementation latitude remains between using the pinned SDK helper behind strict checks and constructing explicit Gophercloud authentication options from the allowed fields. Either choice must prove closed inputs, fixed identity/project, zero authentication for pre-auth rejected/disabled requests, zero resource reads for post-auth identity/scope mismatch, no credential-file fallback, and no secret propagation. A new dotenv/auth-profile parser dependency, credential broker, privilege change, or broader environment-derived policy is outside this decision and requires a separate decision.
